# SRS：功能与非功能需求

> 本套规格是实现的**唯一对外契约**（P4 单向阀）：新增功能、重构或排障都应先回到这里，
> 而不是依赖任何一次性分析材料。判定标准是"第三方开发者不接触对照产品也能据此实现"。
> 其余三份：[架构](architecture.md)、[接口契约](interfaces.md)、[数据模型](data-model.md)。

## 1. 功能需求

| 编号 | 能力 | 必须达成的行为 |
|---|---|---|
| F1 | 目录与检索 | 分类树（含子分类聚合）、中文与拼音搜索、评分与热度排序、运营位、专属应用、捆绑包 |
| F2 | 本机已装清单 | 读 HKLM 64/32 与 HKCU 卸载项；按根隔离失败；落盘缓存 + TTL + 增量刷新；同名多实例按 `regDir` 区分 |
| F3 | 升级计划 | 与目录视图共用同一套名字判据；按最低版本的同名实例决策；空白版本不参与升级 |
| F4 | 残留扫描与清理 | 只读扫描产出报告；注册表类先导出 `.reg` 备份；支持撤销；默认 `dryRun`；文件类可选回收（移动而非不可逆删除）；回收目录有保留策略与清空入口 |
| F5 | 下载 | 断点续传（带 `If-Range`）、瞬时故障重试、按目标路径去重、排队可取消、落地失败原地重试且不重下整包 |
| F6 | 安装/卸载编排 | 多类型执行计划（MSI/INNO/NSIS/脚本）、卸载串正确分词（含空格路径）、MSI 产品码取法正确、任务有终态守护、提权参数不被拆坏 |
| F7 | 申请与审批 | 审批凭证绑定应用**与版本**；有效期不可解析视为无效；吊销对已签发凭证生效；申请人不可自报他人身份 |
| F8 | 本地应用包仓库 | 目录镜像 + `manifest.json`（含快照），离线可审计；按 `size`+`sha256` 校验；缓存命中不发请求 |
| F9 | 自升级 | 发布→检查→暂存→提交四态；应用前校验签名证据；回滚必须有证据，不得静默降级 |
| F10 | UI 与皮肤 | 皮肤 = token 覆盖表，缺省回落要被显式记录；托盘与多窗口；窗口生命周期可回收 |
| F11 | 心跳与机群汇总 | 客户端上报资产摘要；服务端聚合、留存历史、可筛离线节点 |

## 2. 非功能需求

- **N1 零构建**：TypeScript 源码直接由 Node 运行（`--experimental-transform-types`），发布树里不出现构建产物。
- **N2 本地边界**：RPC 桥只绑回环，且校验 `Origin`；管理端点 fail-closed（缺令牌即拒）。
- **N3 失败可见**：任何"按根/按段跳过"都必须进入报告的 `gaps`，且清理计划拒绝不完整报告。
- **N4 跨进程安全**：共享的运行配置与缓存用唯一临时名 + Windows `EPERM` 有界重试；不存在写死的端口/固定临时路径。
- **N5 公开面可复现**：文档配图只能来自虚构清单（`UI_DEMO_FAKE_INVENTORY`）与路径脱敏（`?mask=1`）；不出现真机数据或个人路径。
- **N6 门禁即判据**：文案越界、emoji 基线、引用完整性、用例数下限都由脚本 + 回归用例钉住，不靠人工记忆。

## 3. 兼容性边界（必须与自主设计的分界）

**必须保持互操作**（对外契约，改动需回归用例）：RPC 报文形状（每行一个 JSON 的 IPC 与 HTTP 信封）、
注册表卸载项字段语义（`DisplayName`/`DisplayVersion`/`UninstallString`/`InstallLocation`）、
`.reg` 文本格式、`manifest.json` 的字段含义、MSI/INNO/NSIS 的静默参数约定。

**完全自主设计**（可自由演进）：内部模块划分与端口注入方式、缓存与去重策略、UI 布局与皮肤 token、
审批凭证的签名载荷排布、心跳摘要结构、目录服务端的存储实现。

## 4. 可判定判据：评分与版本比较

> 本节的存在理由：曾有第三方读者只用其余三份规格尝试实现这两项能力，得到 26 条"规格没决定、只能自己假设"的点。
> 规格的可验收定义是**据此即可实现且行为唯一**，所以把这些决定写进规格本身，而不是留给读者猜。

### 4.1 星级分布 `RatingDistribution`

- `buckets` 固定五格（1..5 星），`count` 是五格之和，`mean` 是**按格加权的算术平均**（不是中位数、不是几何平均）。
- 单条评分入参 `stars` 的处理：**先四舍五入，再钳到 1..5**。所以 0.4 计入 1 星、0.6 计入 1 星、5.4 计入 5 星、负数计入 1 星；
  钳制发生在计数之前，越界不会产生第六格或丢条。`±Infinity` 属于"有限语义内的极端值"，按上面的钳制归入 5/1。
- **非有限的 `stars`（`NaN`、或非数字类型）整条丢弃**：既不进桶、也不计入 `count`。
  这不是保守而是必需的：丢掉之前的写法会同时做到「这条不被计数」与「`mean` 变成 NaN」，
  于是**一条坏评分毒掉整个应用的均值**，排序比较拿到 NaN、顺序退化成输入顺序；
  反过来"把 NaN 钳成 1 星"是凭空造出一票，两个方向都不可接受。
- 空分布：`buckets` 全 0、`count` 为 0、`mean` 定义为 **0**（不是 NaN，也不是 null）。
- 已装验证加权：`verifiedInstall` 为真的评分按权重复制 `verifiedMultiplier` 份（默认 **3**），假的不复制。
  这是"真实装过的用户更能主导榜单"的实现方式；它影响 `mean` 与 `count` 两者。
- 同一用户对同一应用重复评分：**不做去重**，按条计入（如需去重属于未来的显式需求，不是现在的默认）。
- `verifiedMultiplier`（默认 **3**）是调用方可覆盖的参数，它的取值域就此写死：
  **0 与负数按 1 处理**（一条真实的已验证评分至少算一票，绝不被抹掉）；
  **非有限值（`NaN` 等）退回默认值 3**。后一条是补的防线——实测覆盖前 `NaN` 会让 `Math.max(1, NaN)` 得 `NaN`，
  复制循环一次都不执行，于是"这条评分存在"却被**静默删除**（`count` 从 1 变 0）。

### 4.6 浮点并列与严格解析的边界（同样是实测读数）

- 「分数相同」指**精确相等**，不做 epsilon 归并：只有先验与票数分布真正算出同一个数才叫并列，此时按 `id` 决胜。
  实测 `4+2` 星与 `3+3` 星的两个应用同为 3.0 ⇒ 并列成立，输出顺序 `a` 在 `z` 前（可复现，不依赖输入顺序）。
- 严格 `parse` 接受的形状：可选 `v`/`V` 前缀、首尾空白被裁掉、前导零按数值（`1.02.3` → `1.2.3`）、
  `+build` 与只留一个 `-` 的尾巴都按「无预发布标签」处理，**且字符串末尾的多余内容不报错**：
  `parse("1.2.3abc")` 成功返回 `1.2.3`。段数少于三段（`1.2`）才判为非法返回 `null`。
- **曾有的不自洽已统一（记录在案）**：同一个 `"1.2abc"` 串，宽松 `parseTolerant` 一度给出 `minor=0`（要求整段都是数字），
  而 `compare` 取「段开头连续数字」读成 `2` —— 一个说这串就是 `1.0.0`，另一个说它比 `1.0.0` 大（`compare("1.2abc","1.2.0") = 0`、
  `compare("1.2abc","1.0.0") = 1`）。现在 `parseTolerant` 采用与 `compare` 同一条规则（段开头连续数字），
  规格承诺两者对任意输入的相对结论一致；`spec-parity-rating-version.test.ts` 里有一条逐串对照的用例钉住它。
  之所以可以直接统一而不必担心行为变更：核过调用方，`parseTolerant` 与严格 `parse` **在生产代码里都没有使用者**，
  只有测试在引用 —— 也就是说这是一处"已导出的公开工具却无人依赖"，改动面无兼容性风险。

### 4.2 平滑（贝叶斯）评分

- 公式：`(priorWeight * priorMean + mean * count) / (priorWeight + count)`。分母为 0 的情况在合法输入下不可达（`priorWeight` 默认 20）。
- 全局先验均值 `priorMean` 由参与排序的**全体应用**共同评分的加权平均得出：`sum(mean_i * count_i) / sum(count_i)`；
  当总票数为 0 时**取 3**（中间值），不是 0，也不是 NaN。
- 先验权重 `priorWeight` 默认 **20**，可由调用方覆盖。
- 因为 `priorWeight` 可被覆盖，**分母为 0 是可达的**（`priorWeight=0` 且该应用无人评分）。规格给的决定是：
  此时返回 `priorMean`，**绝不返回 NaN**——NaN 会让排序比较失去传递性、结果退化成输入顺序，而"没人投票就先按全局均值算"与贝叶斯平滑的本意一致。
  （早先本节写过"分母为 0 在合法输入下不可达"，那是错的：合法与否由调用方参数决定，不由当前默认值决定。）

### 4.3 排序契约

- **"参与排序的应用"就是调用方传入的那个集合，不做任何预筛**：`priorMean` 的样本集 = 该集合全体（**包含被排序者自身**，不
  做 leave-one-out），输出成员也 = 该集合成员，不多不少、不剔除零票应用。这条决定同时决定了两件事，所以必须显式说清：
  先验的取值，以及榜单里会出现谁。
- `rankByQuality`：按 4.2 的分数**降序**；分数相同按 `id` 的字典序升序做唯一决胜（排序必须全序、可复现）。返回 `{id, score}[]`，不返回未参与的应用。
- `rankRecommend`：票数达到 `minVotes`（默认 **5**）的应用用 `quality + log10(downloadCount + 1) * 0.1`；
  票数不足的应用**只用热度** `log10(downloadCount + 1)`（即完全丢弃质量项，而不是把质量当 0 相加）。
  决胜与返回形状同 `rankByQuality`。"热度"就此定义为下载量的常用对数，没有别的口径。
- **下载量的取值域**：`downloadCount` 是外部可写字段，可能为负或非有限值。规定：**非有限或负数一律按 0 计**
  （即"没有下载记录"）。不这么做的后果是实测到的：`log10(-1+1) = -Infinity`、`log10(-2+1) = NaN`，
  而 NaN 进排序比较会让**顺序变成任意**（脏数据那条反而排到第一），等于把榜单交给一条坏记录。
- 目录列表视图（`AppSummary`）**不携带评分字段**；评分与排序只在服务端计算，客户端要分数须显式调用评分接口。

### 4.4 版本号比较

- 输入是任意点分版本字符串。核心判据是**逐段按数值比较，段数不限**（Windows 常见四段，只取前三段会把仅第四段不同的版本误判为相等，从而漏报可升级）。
- 段数不等时，短的一方**用 0 补齐**；每段取开头的连续数字，段内没有数字则该段按 0 计；前导零参与数值比较（`1.02.3` 与 `1.2.3` 相等）。
- 先去掉首尾空白与可选的前缀 `v`/`V`；`+build` 之类的构建元数据在切分主版本时被丢弃，`-` 之后视为预发布标签。
- 主版本各段相等时再比预发布标签：无标签 **大于** 有标签；标签按点分段比较，**纯数字段小于同位的字母段**，长度不等时短的一方小于长的一方。
- 比较函数返回 `-1 / 0 / 1`（不是任意差值）；`gt`/`lt` 由它派生。区间表达式 `parseRange` 支持逗号分隔的多条子句，符号集为 `>= <= > < = !=`（省略符号按 `=`）。
- 严格解析（`parse`）只接受"三段数字 + 可选预发布"，失败返回 `null`；宽松解析（`parseTolerant`）永不失败，缺的段按 0。
  两者是不同用途：前者判"这是不是一个规范版本号"，后者判"能不能比出大小"。
- 空字符串/纯空白在比较路径里按 `[0]` 处理（即等于 `0`）。但**升级计划不接受空版本号**：
  `DisplayVersion` 为空表示"不知道装了哪个版本"，不参与"可升级"判定，也不得以 `0` 的身份去比大小。

### 4.5 版本串的解析细节（以下每条都是**实测读数**，不是设想）

- `+build` 与 `-` 的先后：先按 `[-+]` 切出主数值段，**但预发布标签是从整个去前缀串尾部用 `-…$` 反向取的**。
  构建元数据 `+…` **一律不参与优先级**（与语义化版本一致），因此 `1.2.3+meta-1` 与 `1.2.3` **相等**（实测 `compare = 0`）；
而标签取到第一个 `-` 之后、`+` 之前的整段，所以 `1.2.3-rc.1+build.2` 的标签是 `rc.1` ⇒ 比 `1.2.3` **小**（实测 `compare = -1`）。
（旧实作用「连字符必须一路到串尾」取标签，这两条读法在两个方向上都是反的：`+meta-1` 的尾巴被当成标签判它小，
`-rc.1+build.2` 反而读不出标签判它相等。现已由唯一一把 `splitCore` 统一，并被 `spec-parity-rating-version.test.ts` 钉住。
真机目录里 152 条版本串**没有一条含 `+`**，故此改动对现有数据是零影响。）
  这个组合读法不直觉，所以写死在这里：尾巴上的 `-1` 会被当预发布，即使它前面出现过 `+`。
- 末尾只有 `-` 而没有内容（`1.2.3-`）**算没有标签**，与 `1.2.3` 相等（实测 `compare = 0`）。
- 标签按点分段比较；同段都是数字时按数值、数字段小于字母段（`-1 < -A`）；
  **字母段区分大小写并按码元序**，实测 `compare("1.2.3-A","1.2.3-a") = -1`（`A` 小于 `a`）。不做大小写归一。
- 区间字符串用逗号分隔，多条子句是 **AND**（全部满足才 `satisfies`）。
  实测 `satisfies("1.0.0", ">=0.9.0,<1.0.0") = false`。
- 子句词法容错：允许逗号两侧空白（`">=1.0.0 , <2.0.0"` 解析为 2 条）；
  **不做任何合法性校验** —— 认不出的片段整体当成一个版本号并按 `=` 比较
  （实测 `parseRange("garbage")` 得 1 条 `{operator:"eq", version:"garbage"}`，于是它只会与字面量 `garbage` 相等）。

## 5. 明确不做

行为采集、Web 中间人、锁屏、远程桌面、驱动级进程拦截、静默保活、软件黑白名单强制下发；
多租户 SaaS、移动端、插件市场。演示安装包是占位文件，**绝不在真机执行**。
