## 0. 当前态势小结

**已完成且被测试钉住**：分发全链路引擎 + 服务端 + 桌面 UI 三层同源 + CLI 无头壳，92 个测试文件、
约 455 个 `test()` 用例、`npm run ci` 全链路门禁（含 emoji 基线、用例数下限、文档引用落地、
许可自审）。真机取证已覆盖清单/残留/版本比较/计划任务编码等关键路径。

**本轮多 agent 并行推进已交付**：P1-4 审计导出、P1-2 审批工作台（后端+前端）已落地并测试钉住
（新增 `audit.test.ts` 6 项、`approvals-admin.test.ts` 5 项；详见 [project-status.md](project-status.md) §3.1）。
剩余 P1-1 / P1-3 数据通路已就绪、仅缺管理端视图；P2 工程化项待排期。

**最大短板**：能力几乎是「逻辑 + 自动化测试」验证，**真机端到端的「最后一公里」尚未闭环**——
Tauri 桌面产物未编译、MSIX/归档安装未实机演练、真实升级链路与真实安装包未跑通、开机自启/托盘未
在真实桌面会话验收。换言之：**引擎正确性可信，但「双击即用」的成品尚未形成**。

**推进总目标**：把「逻辑正确」升级为「可在目标环境可信落地」，并补齐工程化与可运营闭环。

## 2. 推进阶段

### 阶段 P0 — 真机端到端闭环（最高优先，决定项目能否「交付」）

> 目标：让核心链路在真实 Windows 环境跑通一次，消除「未验证」清单。

| 项 | 内容 | 验收标准 | 依赖 |
|---|---|---|---|
| P0-1 | **Tauri v2 编译验证** | `npm run icons` → `npm run tauri build` 产出自有 exe/安装包；桌面窗口在 Tauri 壳内正常渲染、RPC 桥连通 | Rust + MSVC + WebView2 工具链 |
| P0-2 | **真实安装包端到端** | 用 `npm run discover` + `npm run build:real-catalog` 灌入本机真实安装包，跑通「下载(或本地仓库命中) → 校验 → 安装 → 装后回读版本」完整链路 | 一台含真实安装包的 Windows 机 |
| P0-3 | **MSIX / 归档安装实机演练** | `runner` 的 MSIX/归档分支在真机执行一次成功 + 一次失败路径，回读与清理正确 | P0-2 的真实包样本 |
| P0-4 | **真实升级链路演练** | 对一真实应用制造「旧版→新版」，跑通 `upgrade.plan` → 安装 → 回读版本提升 → 旧版残留可选清理 | P0-2 |
| P0-5 | **开机自启 + 托盘桌面验收** | 真实桌面会话下托盘图标显示/菜单动作回传、开关写入 `HKCU\...\Run` 且可关闭、窗口关闭即退出 | P0-1 或 `--app` 桌面壳 |

> 每个 P0 项完成后，把「真机取证数据」回填进 `docs/assets/`（脱敏）与 `CHANGELOG`，并补一条
> 「真机验收」回归用例（如 `desktop-acceptance.*` / `install-real-smoke.*`），使 CI 不再只信模拟器。

### 阶段 P1 — 可运营闭环（决定项目能否「长期用」）

| 项 | 内容 | 验收标准 |
|---|---|---|
| P1-1 | **机群运营面板** | 基于 `GET /api/admin/fleet` 的管理端视图：覆盖率/到达率/离线节点看板；数据来自已验证的心跳摘要，不采集行为（端点/facade/dispatch 已就绪，仅缺管理端视图） |
| P1-2 [完成] | **审批工作台** | [完成] 已交付：管理员全量工单 + 受理/驳回/吊销闭环（`approval.listAll`/`decide`/`revoke`），Web 工作台视图已接入；**前端真实桌面渲染验收**见 P0-5 |
| P1-3 | **部门目录治理** | 部门可见范围的可视化配置与回归用例；越权访问被 `fail-closed` 拦截（数据通路已就绪，仅缺管理端视图） |
| P1-4 [完成] | **审计导出** | [完成] 已交付：`GET /api/admin/audit` + 导出 CSV/JSON，banners/bundles 写入已补审计（关键动作不漏记） |
| P1-5 | **安装包分发规模化** | `Range` 下载在慢网/大包下的稳定性与并发上限压测；`localrepo` 镜像在多版本、多机的一致性 |

### 阶段 P2 — 工程化与体验增强（锦上添花，可并行）

| 项 | 内容 |
|---|---|
| P2-1 | **自动化覆盖率度量**：从「用例数下限」升级为语句/分支覆盖率门槛（仍防退化） |
| P2-2 | **跨平台 CI 增补**：Linux 作业已存在，可加 macOS 作业校验平台无关面 |
| P2-3 | **主题/皮肤市场雏形**：token 覆盖表的导入/导出与预览（注意 `validateTokens` 边界） |
| P2-4 | **性能预算**：清单首屏、残留扫描、首页渲染的耗时预算纳入 CI 断言（复用 `measure:*` 脚本） |
| P2-5 | **可访问性（a11y）**：键盘可达、对比度、屏幕阅读器标签，配合 emoji 基线已有的 SVG 内联图标 |

## 3. 需要决策/外部输入的事项（阻塞点）

1. **目标交付形态**：桌面产物走 Tauri（需工具链投入）还是暂以 `--app` 窗口 + 安装器打包？
   影响 P0-1 与 P0-5 的优先级。
2. **真实安装包来源**：演练 P0-2/3/4 需要真实 Windows 机与若干常见安装包（含 MSIX 样本）。
   是否提供测试机/样本清单？
3. **运营部署拓扑**：目录服务端是中心化 SaaS 还是企业内网私有部署？影响 P1 的鉴权/部门目录尺度。
4. **许可白名单**：若后续需要新依赖（如 Tauri 相关、UI 组件库），先确认 `check:licenses` 白名单是否放行。
5. **文档受众**：是否需要面向「终端用户」的使用手册（当前 wiki 偏开发/协议向）？

## 4. 推进节奏建议

```
现在 ──P0(真机闭环, 2~4 周)──► 可交付的桌面成品
        │
        ├─P1(运营闭环, 并行)──► 可长期运营
        │
        └─P2(工程化, 持续)──► 可持续演进
```

- **P0 是硬门槛**：未过 P0，项目停留在「引擎可信、成品未证」；建议集中资源先清空 P0 五项的真机验收。
- **P1 与 P0 可部分并行**：审计导出(P1-4)、审批工作台(P1-2) 已交付；机群面板(P1-1)、部门治理(P1-3) 数据通路就绪仅缺管理端视图，可在真机验收进行的同时推进。
- **P2 不设硬截止**：在不破坏现有门禁（emoji/用例下限/引用落地）前提下增量引入。

---

## 5. 完成定义（Definition of Done）

本轮推进视为「阶段达标」当且仅当：

1. P0-1~P0-5 全部有**真机验收记录**且对应回归用例进入 `npm test`；
2. `README`「未完成」清单清空或每项标注明确阻塞原因与负责方；
3. `CHANGELOG` 切出新的语义化版本（建议 `0.2.0`），且 `docs/project-status.md` 已据实刷新；
4. 任一新增/变更能力**先更新 SRS/接口/数据模型三件套**，再合入——P4 单向阀不被绕过。
